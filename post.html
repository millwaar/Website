TL;DR: Ingest Wiz issues into Sentinel, normalise the resource ID, join it against Defender for Cloud and Defender XDR alerts, then let an automation rule raise severity when a live alert lands on a resource that is already part of a Wiz toxic combination.

Why bother correlating?

Wiz is excellent at telling you what could happen: a public VM with a critical CVE and an identity that can read your customer data. Defender is excellent at telling you what is happening: a suspicious process, a credential dump, an anomalous sign-in. On their own, both create queues. Together they answer the question your SOC actually cares about: is this alert sitting on an attack path to something that matters?

An alert on a throwaway dev box and the same alert on vm-web-01, one hop from a storage account full of PII, should not have the same priority. This article wires that context into Sentinel so the triage analyst sees it straight away.

Architecture

  • Wiz → Sentinel: the Wiz solution from the Sentinel Content Hub pulls issues, vulnerabilities and audit logs into custom tables.
  • Defender for Cloud & Defender XDR → Sentinel: native connectors land alerts in SecurityAlert and incidents in SecurityIncident.
  • Correlation: a scheduled analytics rule joins the two on a normalised Azure resource ID.
  • Response: an automation rule tags and escalates matching incidents, and a playbook posts the Wiz graph link to the incident.

Step 1: Ingest Wiz issues

Install the Wiz solution from Content Hub and configure the connector with a Wiz service account scoped to read:issues and read:vulnerabilities. Keep the scope tight: this account is a credential stored in your SIEM, so treat it as one.

Once data is flowing, check the shape of what has arrived:

check-ingest.kql
WizIssues_CL
| where TimeGenerated > ago(1d)
| summarize Issues = count() by Severity, Status
| order by Issues desc

Check your column names. Table and column names depend on the connector version. Run getschema against the table before you copy the queries below.

Step 2: Normalise resource IDs

Azure resource IDs are case-insensitive, and different products disagree on casing. Lower-case everything and wrap it in a reusable function, saved as WizCriticalResources:

WizCriticalResources.kql
WizIssues_CL
| where Status == "OPEN"
| where Severity in ("CRITICAL", "HIGH")
| summarize arg_max(TimeGenerated, *) by IssueId
| extend ResourceId = tolower(ResourceId)
| project ResourceId, IssueId, WizIssue = Title, Severity, WizUrl

Step 3: Correlate with live alerts

Now the scheduled analytics rule. Run it every 15 minutes over a one-hour lookback, and map ResourceId to an Azure Resource entity so it shows up on the incident graph.

rule-wiz-toxic-alert.kql
// Live alert on a resource that is part of a Wiz toxic combination
SecurityAlert
| where TimeGenerated > ago(1h)
| mv-expand Entity = todynamic(Entities)
| extend ResourceId = tolower(tostring(Entity.ResourceId))
| where isnotempty(ResourceId)
| join kind=inner WizCriticalResources on ResourceId
| summarize Alerts = make_set(AlertName),
            WizIssues = make_set(WizIssue),
            WizLinks = make_set(WizUrl)
    by ResourceId
| extend Severity = "High"

Step 4: Automate the response

Create an automation rule that triggers on incidents from this analytics rule and:

  1. Adds the tag wiz-toxic-path so it can be filtered in workbooks.
  2. Assigns it to your cloud response tier rather than the general queue.
  3. Runs a playbook that comments the Wiz graph links on the incident, so the analyst can open the attack path in one click.

If the resource is a VM onboarded to Defender for Endpoint, consider a second playbook that offers device isolation behind an approval step. Isolation is very effective, and a misfire on a production web tier is very visible.

What good looks like

After a month in production you should see a small number of high-fidelity incidents, each with a clear story: this alert, on this resource, which reaches that data. If the rule is noisy, the fix is almost always in Wiz: tighten which issue rules count as toxic, rather than piling exclusions into KQL.
